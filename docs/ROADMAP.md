# Nutstore MCP 后续开发任务与 Cursor 执行指引

更新日期：2026-10-11

项目目录：本仓库根目录

本文件是后续任务清单，不代表其中的待办功能已经实现。Cursor 应先核对实际代码，
按优先级逐阶段完成，在本文件和 `installation.md` 中记录验证证据。

## 1. 目标与现状

目标链路：坚果云 → WebDAV → Nutstore MCP Server → Cursor / Claude / AI Agent。
先让 AI 能浏览、找到并读取资料，再逐步实现有来源的知识库问答。

| 阶段 | 功能 | 当前状态 |
| --- | --- | --- |
| v0.1 | 连接检查、目录列举、文本读取、文件名搜索 | 已实现；新增工具的 Cursor 验收待完成 |
| v0.2 | Markdown/PDF 解析、文档索引、正文全文检索 | 正文关键词检索已实现；结构解析、PDF 与索引仍待开发 |
| v0.3 | Embedding、语义检索、RAG | 待开发 |
| v1.0 | Docker、pip 发布、GitHub Release、MCP 生态发布 | 待完成；本地 wheel 已可构建 |

当前工具：`check_connection`、`list_directory`、`read_file`、`search_file`、`search_content`。
其中 `search_file` 只按文件名匹配，不搜索正文；`search_content` 在文本正文中搜索
一个连续子串，返回相对路径、行号和命中片段。`read_file` 返回 UTF-8 文本原文，
支持 BOM 和指定文本后缀；默认上限 256 KiB，硬上限 1 MiB。
Markdown 原文读取与正文关键词检索已经具备；结构解析、文档索引和 PDF 仍待开发。
当前没有缓存、增量索引或后台同步，每次文件名搜索需要查询远端目录。

已有验证记录：本地 pytest 最近一次完整运行 73 项通过，依赖检查和本地 wheel 构建通过；
真实 MCP 子进程已注册五个工具，并成功调用既有工具，读取过一份 7115 字节的 Markdown 文件。
这些是本次开发记录，后续改动后必须重新运行相关验证。
早期 Cursor 验收仅覆盖连接检查和目录列举，不能代替新增工具验收。

## 2. 开发原则

- 复用现有架构：`config.py` 管配置，`webdav.py` 管远端访问，`server.py` 注册工具，
  `smoke.py` 验证 MCP 链路。新模块仅在责任确实独立时增加，避免大规模重构。
- 保持只读能力；上传、覆盖、移动、删除远端文件不在本路线范围内。
- 保留四个现有工具的语义；正文搜索新增独立接口，不能把 `search_file` 悄悄改为全文搜索。
- 路径保持相对于 WebDAV 根目录，维持路径校验、请求超时、读取和扫描预算。
- 不恢复目录 HEAD 预检查：实际坚果云子目录可能 HEAD 403、PROPFIND 207。
- 保留目录响应校验和禁止重定向行为，不能将 HTML/畸形 XML 错误页误报为空目录。
- stdio 的 stdout 仅用于 MCP 协议；日志写 stderr，不输出账号、密码或默认打印私有正文。
- `.env` 仅在本机使用；不要覆盖已有配置，不将凭据、正文索引、缓存、向量数据打进安装包。
- 遇到 Bug 先定位根因并写回归测试，不能用宽泛 try/except 或删功能掩盖错误。
- 遵循 Apache 2.0，归属统一为 `Copyright 2026 Neville`；新增依赖检查许可证兼容性。
- 当前目录此前没有 Git 仓库。接手时重新核对；不要假定已存在分支、远端或发布权限。
- 每次只推进一个可验收阶段；新增技术或优化建议记录在末尾，不擅自扩展范围。

## 3. P0：完成 v0.1 客户端验收及可靠性补充

- [ ] 在 Cursor 重新加载/重启 nutstore 服务，确认发现四个工具。
- [ ] 在指定知识库子目录调用 `search_file` 查找已知文本文件，再使用完整相对路径调用
  `read_file`，对照原始文件核验中文、换行和正文完整性。
- [ ] 验证一次扫描截断结果，确认 `truncated` 和 `limit_reasons` 提示可被客户端识别。
- [ ] 补充空目录、缺失查询集合 href、异常 DAV 子项状态的回归测试。
- [ ] 检查 PROPFIND 子项 `status`/`propstat` 及 href 的直接子项关系，异常不能被压缩为
  看似正常的文件名。改善时保留真实坚果云兼容性，并控制改动范围。
- [ ] 更新 `docs/installation.md`，分别记录自动测试、真实服务、Cursor 界面结果。

验收标准：现有功能无回归；新增工具在 Cursor 实际调用成功；错误响应不被误报为
正常空目录；未完成或失败的步骤保留未勾选状态。

## 4. P1：先实现文本正文检索，再完善增量索引

### 4.1 正文关键词检索

- [x] 先实现有界的 Markdown/TXT 正文关键词搜索，返回来源相对路径、命中片段和行号。
- [x] 使用独立的正文搜索工具；建议名称 `search_content`，接口设计在编码前简要说明。
- [x] 明确中文匹配、大小写处理、多关键词含义及结果顺序，先使用简单可验证的匹配规则。
- [x] 限制扫描文件数、每文件字节数、总读取量、结果条数和执行时间，避免无界下载知识库。
- [x] 明确报告扫描不完整、超限、非 UTF-8、权限错误、文件读取失败等情况；不能静默
  跳过后声称“没有找到”。单个文件异常能否继续搜索，应由明确的返回契约和测试决定。
- [x] 默认返回有限命中片段，不能把每份文档的完整正文塞进搜索响应。
- [x] 使用本地 WebDAV 测试服务和真实 MCP 子进程验证，不让自动测试依赖个人账号。

验收标准：准备一个“文件名不含关键词、正文含关键词”的文件，正文搜索必须找到它；
不含关键词的文件不能误命中。中文、空结果、重复关键词、超限、失败与截断都有测试。
现有 `search_file` 行为不变，Cursor 可以从命中路径继续调用 `read_file`。
自动测试和 MCP 子进程已覆盖 search_content。Cursor 从命中路径调用 read_file 尚未发生，不能把本节验收标准全部视为通过。

### 4.2 文档索引与增量更新

- [ ] 基于上一阶段已明确的检索契约增加本地持久化索引，减少重复远端下载。
- [ ] 文档记录至少包含来源路径、修改时间、大小、可用时的 ETag、内容哈希和索引状态。
- [ ] 首次扫描建立索引；后续同步区分新增、变更、未变更、删除、读取失败和待重试。
- [ ] 只有可信的完整扫描才能判定文档被删除；扫描截断、网络错误或无权限时不能
  将未看到的文件当成删除，避免错误清空索引。
- [ ] 未变更文档尽量不重新下载；若元数据不足，使用明确的保守策略，不能假装能准确判断。
- [ ] 索引更新保证一致性，失败后保留可恢复状态；提供手动同步、状态查看和重建入口。
- [ ] 索引与缓存可清理、可配置位置，排除在 Git 和构建产物之外。
- [ ] 初版优先手动更新，不默认启动全库后台轮询。选用数据库或搜索组件前验证中文检索。
- [ ] 检索返回索引更新时间和覆盖范围，区分远端新内容与尚未同步的本地结果。

验收标准：首次同步、无变更同步、文件修改/新增/删除、失败重试及不完整扫描都有
确定的测试；无变更同步不重复下载正文；重启后索引仍可用；结果明确说明新鲜度。

## 5. P2：Markdown 结构解析与 PDF 支持（v0.2）

### 5.1 Markdown 知识库

- [ ] 在原文读取基础上提取标题层级、段落、代码块、链接；根据实际样本支持 frontmatter。
- [ ] 分块保留来源路径、标题上下文和原文行号，不破坏代码块、公式或正文引用位置。
- [ ] 普通 Markdown 优先；Obsidian 双链、标签和附件引用仅在需求与样本明确后支持。
- [ ] 保留 `read_file` 的原文语义；解析结果供索引/检索使用，避免解析与原文互相覆盖。

验收标准：中文笔记、代码块、公式、空文件及无 frontmatter 文件可正确处理；
命中块可以追溯到原文，解析不把文档中的指令当成 Agent 操作要求。

### 5.2 PDF 解析

- [ ] 增加独立 PDF 读取/解析能力，不让文本 `read_file` 强行解码 PDF 二进制。
- [ ] 先支持有文本层的 PDF，保留来源路径和真实页码；记录解析器及其限制。
- [ ] 对文件大小、页数、下载量和解析时间设置上限。
- [ ] 加密、损坏、空文本、复杂排版等情形给出可解释结果。
- [ ] 扫描版 PDF 明确报告需要 OCR，不能将“未提取到文字”误报为“文档没有内容”。
  OCR 作为可选后续任务，不默认引入新服务。
- [ ] PDF 文本接入现有索引与搜索链路，命中返回页码和片段。

验收标准：用本地测试 PDF 验证英文/中文、页码、多页、超限、损坏文件和扫描版识别；
Cursor 能检索并定位已知 PDF 内容。复杂表格和公式的提取限制写入文档。

Word 解析不是原始版本路线的必选项，当前仅列为待确认需求，不纳入本轮任务。

## 6. P3：Embedding、语义检索与 RAG（v0.3）

- [ ] 先建立小型测试问题集，与正文关键词检索比较，明确语义检索要解决的实际问题。
- [ ] 实现前明确本地模型/外部服务选择、正文是否离开本机、成本与隐私范围。
  涉及 API 凭据时按当前环境的凭据配置流程处理，不读取或输出现有密钥。
- [ ] 以已验证的文档块为单位生成向量，记录模型、维度、分块版本和来源。
- [ ] 实现增量向量更新、文档删除后的失效处理，以及模型变更后的重建策略。
- [ ] 新增语义检索工具，返回有限数量的来源块、相似度及文档定位信息。
- [ ] RAG 先提供可引用的检索上下文，由 Cursor/Claude/Agent 生成回答；仅在明确需要时
  增加服务器端生成模型，避免默认引入第二套聊天服务。
- [ ] 回答要求引用真实文件和行号/页码；证据不足时明确说明，不能编造资料支持。
- [ ] 将知识库正文当作资料，测试文档中的恶意操作指令不会触发越权工具使用。

验收标准：问题集覆盖同义表达、中文领域术语、无相关证据、旧索引和多来源冲突；
对比关键词基线，报告检索命中及来源准确性，不能只用“回答看起来合理”作为通过标准。

## 8. 每个阶段的执行与交付要求

1. 先读 `README.md`、`docs/architecture.md`、`docs/installation.md` 和相关代码/测试，
   核实状态；先处理 P0，再推进 P1，不能一次搭建全部后续版本。
2. 编码前用少量步骤说明当前阶段的目标、接口、修改文件和验证方式。
3. 重要行为先写测试，观察预期失败，再实现最小改动；新依赖说明用途与取舍。
4. 测试优先使用本地 WebDAV 和真实 MCP 子进程；真实账号验证限定范围，避免全库扫描。
5. 通过必要检查后更新任务复选框、README 和验收记录，注明哪些结果来自自动测试、
   真实服务或客户端实际调用，不能将某一层通过当成所有层都通过。
6. 完成后简要说明做了什么、为什么这样做、如何验证，以及用户值得理解的 1～3 个知识点。

基础验证命令（PowerShell，项目根目录）：

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -X utf8 -m nutstore_mcp.smoke
.\.venv\Scripts\python.exe -m pip wheel . --no-deps --wheel-dir dist
```

`smoke` 默认只调用连接和目录工具，同时检查四个 v0.1 工具已注册；
新增接口后同步扩展客户端检查。按 README 的可选参数单独验证读取/文件名搜索，
注意该命令会打印正文。基础命令成功不自动等于新功能的专项测试或客户端验收成功。

> 不提前加入 PDF、Embedding、RAG 或 Docker，也不发布任何外部产物。
> 完成后更新本文件任务状态和验收记录，说明验证证据、限制和关键知识点。
